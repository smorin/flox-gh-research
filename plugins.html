flox-hello-script · flox-hello-binary · flox-hello-local

Three extensions, three install paths

Each reference repo exists to prove exactly one path through the installer works. They are deliberately trivial — the interesting content is not what they do, but what each one has to contain in order to be installable at all.

Extensions are a beta feature and off by default. Every flox extension … command below requires beta to be enabled, and flox <name> dispatch specifically requires the environment variable:

export FLOX_FEATURES_BETA=true

The script and local extensions ship byte-identical logic on purpose. Both are the same seven-line bash script differing only in a default name. That is good experimental design: holding the payload constant means any behavioral difference between them is attributable to the install path, which is the only thing they are meant to test.

flox-hello-script — the minimum viable extension

flox/flox-hello-script

Script kind · installs as the hello-script extension · invoked as flox hello-script

This is the shape an extension takes when nothing is required of it. Five files, of which two are a licence and a CI workflow:

tracked files
flox-extension.toml       3 lines
flox-hello-script         7 lines · executable, bash
README.md
LICENSE
.github/workflows/ci.yml

The naming rule is doing quiet work here. The repo is flox-hello-script, so the name is hello-script, so the executable must be called flox-hello-script — repo name, extension name, and executable name are one string in three places. Getting that wrong is the first mistake an author makes, and it was the first mistake made here: commit 7305785 is rename executable to flox-hello-script to match derived name.

flox-extension.tomlcomplete
[extension]
name = "hello-script"
description = "Canonical script-kind reference extension for flox."

No schema, no kind, no [environment]. The serde default supplies the schema, probing supplies the kind, and an absent environment stanza means Inherit.

flox-hello-scriptcomplete
#!/usr/bin/env bash
set -euo pipefail

name="${FLOX_EXTENSION_NAME:-hello}"
version="${FLOX_EXTENSION_VERSION:-unknown}"

echo "Hello from ${name} v${version}"
if [ "$#" -gt 0 ]; then
  echo "args: $*"
fi

Two things worth copying from those seven lines. It reads its own identity from FLOX_EXTENSION_NAME rather than hardcoding it, with a fallback for when it is run directly outside flox — so the same file works both as an installed extension and as a script you can execute to debug. And it echoes $*, which is what demonstrates that arguments after the extension name are forwarded untouched.

What its commit history teaches

Three commits, and two of them are corrections that every new author will need:

  1. 84b46cf — the initial extension.
  2. 7305785 — rename executable to flox-hello-script to match derived name. The executable filename is not free; it is derived from the repo name.
  3. c8d5f41 — drop phantom kind field; don't require optional description. The author had written kind = "script" following the design document. The shipped parser has no such field, so it was inert.

The README did not follow its own fix. README.md still describes the repo as "a flox-extension.toml manifest declaring kind = "script"" — the exact field commit c8d5f41 removed. Its usage examples also say flox extension upgrade hello and remove hello, though the extension is named hello-script. Neither breaks anything, and both would mislead someone copying from the canonical example.

flox-hello-binary — the release pipeline

flox/flox-hello-binary

Binary kind · tagged v0.1.0 · macOS only at this version

The same program, in Rust, with everything that shipping a compiled artifact demands:

tracked files

src/main.rs                   19 lines · same behavior as the bash script

.github/workflows/ci.yml
PROJECTS.md                    tracks Linux support as P02
README.md · LICENSE · .gitignore

src/main.rs is the bash script transliterated — read FLOX_EXTENSION_NAME and FLOX_EXTENSION_VERSION from the environment with fallbacks, print a greeting, echo any arguments. Nineteen lines including a smoke test. The point was never the program.

flox-extension.tomlcomplete
schema = "1"

[extension]
name = "hello-binary"
description = "Canonical binary-kind reference extension for flox"

[extension.binary]
source = "github-release"
asset = "flox-hello-binary-{os}-{arch}.tar.gz"

The asset template here is inert: install selects the binary by substring-matching platform tokens against the release's asset names and never consults the manifest template (see the manifest page). The workflow below names its assets flox-hello-binary-macos-aarch64.tar.gz, and the macos token is what the substring matcher finds — the template's {os} rendering plays no part.

The release workflow

Tag-triggered on v*.*.*, a two-job build-then-release split, with one detail worth stealing:

.github/workflows/release.ymlexcerpt
jobs:
  build:
    runs-on: macos-latest              # ← both arches built on one runner
    strategy:
      fail-fast: false
      matrix:
        include:
          - target: x86_64-apple-darwin
            asset_arch: x86_64
          - target: aarch64-apple-darwin
            asset_arch: aarch64
    steps:
      - uses: dtolnay/rust-toolchain@stable
        with:
          targets: ${{ matrix.target }}

      - run: cargo build --release --target "$TARGET"

      - name: Stage archive
        run: |
          asset="flox-hello-binary-macos-${ASSET_ARCH}.tar.gz"
          staging=$(mktemp -d)
          cp "target/${TARGET}/release/flox-hello-binary" "$staging/flox-hello-binary"
          tar -C "$staging" -czf "$asset" flox-hello-binary
          shasum -a 256 "$asset"       # ← printed to the log, not published

  release:
    needs: build
    runs-on: ubuntu-latest             # ← cheap runner, only calls the API
    steps:
      - uses: actions/download-artifact@v4
        with: { path: dist, merge-multiple: true }
      - run: gh release create "$TAG" --repo "$REPO" dist/*.tar.gz

Three decisions in there are worth carrying into any real extension:

  • Both macOS architectures cross-compile from one runner. Commit 69236a5 is the fix that made this so — cross-compile both macOS arches from macos-latest. Apple's toolchain targets both from either host, so a matrix over target rather than over runs-on halves the runner cost.
  • The archive is staged so it contains exactly one file at the root. The binary is copied to a temp directory and archived from there, so it unpacks as flox-hello-binary and not target/aarch64-apple-darwin/release/flox-hello-binary. flox looks for the executable by name after extraction; a nested path would not be found.
  • The release job runs on Ubuntu. It only downloads artifacts and calls the GitHub API, so paying for a macOS runner to do it would be waste.

The macOS-only limitation

v0.1.0 ships two assets, both macOS. This is scoped rather than forgotten — the repo's own PROJECTS.md tracks Linux as P02, and puts Windows explicitly out of scope on the grounds that flox's own platform matrix does not include it yet.

The practical consequence: this reference extension cannot be installed on Linux. Anyone learning the binary path on a Linux machine will hit a no release asset matches error that is correct but discouraging. Flagged on the risks page.

flox-hello-local — the loop authors actually live in

flox/flox-hello-local

Local kind · never installed from GitHub · exercises --from-path

Structurally identical to flox-hello-script — same five files, same three-line manifest, the same bash script with a different default name. The difference is entirely in how it gets installed.

the local authoring loop
git clone https://github.com/flox/flox-hello-local
cd flox-hello-local

flox extension install --from-path .      # copies out of this working tree
flox hello-local world
# Hello from hello-local v<commit>
# args: world

$EDITOR flox-hello-local                  # change something

flox extension install --from-path . --force   # re-register
flox hello-local world                    # see the change

--from-path skips GitHub entirely: no clone, no release lookup, no network. The installer reads flox-extension.toml from the working tree for the name, or derives it from the directory basename by stripping a leading flox-.

Why upgrade refuses, and why that is right

A local install copies the executable and manifest out of your working tree into ~/.local/share/flox/extensions/flox-hello-local/ (fs::copy). There is no remote to compare against and no version to advance to — upgrade would be meaningless. Rather than silently succeed, it refuses and says so.

It is a copy, not a symlink — so edits do not take effect until you reinstall. Because --from-path copies the files into the managed directory, editing the script in your working tree changes nothing until you re-run flox extension install --from-path . --force. That is exactly why the reference README's dev loop uses --force after every edit. (An earlier draft of these pages claimed the executable was symlinked and edits were live; that was wrong.)

Which one should you write?

Start local, always

Whatever you are ultimately shipping, develop with --from-path. No push, no tag, no release, no waiting on CI. Move to a published kind only when someone else needs to install it.

Ship as script by default

Bash, Python, Ruby, Node — anything with a shebang. No build, no release engineering, and users can read the source before running it, which matters given that extensions are unsandboxed. Most extensions should stop here.

Ship as binary when you must

Rust, Go, C — where clone-and-run is not viable. You are taking on a release pipeline, a platform matrix, and the obligation to build for every architecture your users have. Copy the workflow above and add Linux from the start.
