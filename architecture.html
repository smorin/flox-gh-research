What was actually built

Nine modules of domain logic, six of command surface, and a two-phase parser trick that makes flox anything work without touching the existing parser. This page describes the code as it stands, not the design it came from.

The constraint that shaped everything

PROJECTS.md opens with seven binding design constraints, and they explain most of the structural decisions below. The subsystem is purely additive: no refactors of adjacent code, no new cross-cutting abstractions, no modifications to flox-activations or flox-core, no new environment-variable conventions, and no new dependencies without checking Cargo.lock first.

Additive by construction, not by discipline. The whole subsystem sits behind the pre-existing features.beta flag, one variant on the BetaCommands group, and a six-line hook in main.rs. It is off by default and hidden from flox --help, so a stock build behaves exactly as it does today.

The predecessor branch did the opposite — it added its own Features::extensions field defaulting to on, with an env-var opt-out, and a top-level Commands::Extension variant. Reusing the existing beta flag removed the Features edit entirely and dropped five per-handler gates to zero, because the Commands::Beta arm gates once before dispatching.

One constraint is worth calling out because it is a real API-design opinion. Adding Commands::Extension(...) to the top-level enum touches only the bottom of that enum; adding the same commands under an existing group enum would have mutated a structure belonging to unrelated commands. The additive change was chosen precisely because it is the one that cannot disturb anything else.

Crate split

Two homes. Command parsing and user-facing presentation live in the flox binary crate; domain logic lives in the beta crate, where it is testable without a bpaf context. This mirrors gh keeping pkg/extensions/ separate from pkg/cmd/extension/.

The domain half deliberately does not live in flox-rust-sdk. The repo's own adding-beta-subcommand skill states that changes outside cli/beta "require more thorough review which will make it slower to add the beta command." Relocating cost almost nothing — across 5,500 lines the module had three crate:: imports, all public SDK API — and bought a completely untouched SDK.

The command half could not follow it: it needs subcommand_metric!, utils::message, SHELL_COMPLETION_DIR, and utils::active_environments, none reachable from beta without a dependency cycle, since flox already depends on beta.

The two-phase parse

For flox hello world to reach a flox-hello executable, the parser must tolerate a subcommand it does not know. bpaf has no equivalent of clap's allow_external_subcommands, and the design document rejected the obvious workaround — a catch-all variant using bpaf::any ordered last — because bpaf evaluates alternatives left to right and a greedy catch-all would swallow legitimate unknown-flag errors, degrading error messages for ordinary typos.

What shipped instead: parse normally, and only on failure ask whether the failure looks like an extension invocation.

the fallback in main.rs, on parse failure
bpaf::ParseFailure::Stderr(m) => {
    //  Parse failed. Try extension dispatch first; a miss falls
    //  through to the unchanged error below.
    if let Some(exit) = commands::extension::try_dispatch_external() {
        return exit;              // dispatched (execvp never returns on success)
    }
    message::error(format!("{m:80}"));
    return ExitCode::from(1);
}

The ordering is the whole point. Built-in parsing is attempted first and its error messages are preserved verbatim, so a user who types flox instal still gets the parser's suggestion rather than "no extension named instal". try_dispatch_external itself returns None immediately unless FLOX_FEATURES_BETA is set, then skips any leading flags and takes the first non-flag token as the name — so flox -v myext can dispatch, not only a bare first positional. On a miss, the original parse error prints and the process exits 1.

Why managed-directory-first is a decision, not a detail

The module comment on dispatch.rs states the reasoning directly: the managed directory is populated only by flox extension install, so precedence there reflects explicit user intent rather than ambient shell state. A stray flox-deploy that happens to be on someone's $PATH cannot silently shadow the one they deliberately installed.

find also rejects any name that is empty or contains a path separator before it composes a path, which forecloses flox ../../something reaching the filesystem.

The exec is a replacement, not a spawn

This diverges from the design document, and it is an improvement. The design described spawning a child process with tokio::process::Command and propagating its exit code. What shipped calls execvp(2) — the flox process is replaced by the extension.

Signals, exit codes, terminal control, and job control all pass through natively because there is no longer a parent to mediate them. The one thing to know when debugging: after flox hello dispatches, there is no flox process left to inspect.

The three activation modes

This is the piece with no gh equivalent. resolve_mode is a pure function from the manifest's [environment] stanza to one of three variants, and it is deliberately lenient — an unrecognized mode value logs a warning and falls back to Inherit rather than failing dispatch, so a manifest written against a future schema degrades instead of breaking.

Inherit

The default

Runs inside whatever activation the caller has, or none. Every FLOX_* variable is preserved. Selected when the stanza is absent, when mode = "inherit", when mode is empty, and as the fallback for any value the parser does not recognize.

None

Deliberately blind

Every variable whose name starts with FLOX_ or _FLOX_ is dropped before exec. For diagnostic tools that must report on flox state without being influenced by it, or auditors that need a clean baseline.

Pinned(ref)

Author's environment wins

Wraps the call in flox activate -r <owner>/<env> -- unless the caller is already inside that exact environment, in which case it execs directly. Requires a non-empty inherit_name.

Two details in the scrubbing that are easy to get wrong

FLOXHUB_* survives None mode. The filter matches FLOX_ and _FLOX_ as byte prefixes, which does not match FLOXHUB_. The module comment says this is intentional: None mode exists to hide the enclosing environment, not to strip FloxHub credentials. An extension in None mode can still authenticate.

Bookkeeping variables are overlaid after scrubbing, in all three modes. An extension always receives these four, and the reference extensions read them rather than hardcoding their own identity:

VariableValue
FLOX_EXTENSION_NAMEThe extension's declared name.
FLOX_EXTENSION_VERSIONThe tag if one is recorded (not gated on --pin), else the 8-char short SHA, else -.
FLOX_EXTENSION_PATHAbsolute path to the install directory for a managed extension; for a $PATH-fallback extension it is the executable path instead.
FLOX_BINPath to the flox binary that dispatched it — the analog of gh's GH_PATH, so extensions can call flox back without $PATH ambiguity.

Where the idempotency check lives, and why

When an extension pins an environment the caller is already inside, re-activating would be wasteful and possibly wrong. That check reads _FLOX_ACTIVE_ENVIRONMENTS and lives on the CLI side rather than in resolve_mode. The stated reason is that keeping it out of the SDK avoids duplicating the ActiveEnvironments JSON parser — the SDK function stays a pure, trivially testable mapping, and the impure lookup happens once at the boundary.

A mismatch — caller inside a different environment than the pinned one — is governed by [on_active] inside. The default, "override", wraps with flox activate -r unconditionally. "error" refuses with a PinnedEnvMismatch whose message names the exact command needed to trust the environment first.

On-disk layout

$XDG_DATA_HOME/flox/extensions/ · from layout.rs
<flox.data_dir>/extensions/
├── .lock                       fslock; serializes install/remove/upgrade
└── flox-<name>/
    ├── flox-<name>             executable · a copied file, or inside a clone
    ├── state.toml              InstalledState, written by install
    ├── flox-extension.toml     copy of the author manifest
    └── .git/                   script and git kinds only

Four functions, sixty-three lines, and no cleverness: extensions_root, install_dir, state_path, lock_path. The name is embedded in the directory (flox-hello/) and repeated in the executable (flox-hello/flox-hello), which is what makes find a single join and a stat rather than a directory scan.

Reads are lock-free; only mutations take .lock. That is safe because state.toml writes are atomic via temp-file rename. Note one thing the design document specified that was not built: an index.toml caching name to install directory. It proved unnecessary once lookup became a single path join.

A lock discipline note from CLAUDE.local.md worth carrying forward. LockGuard is non-reentrant. It must be acquired once at the top of a mutating operation, before any kind-dispatch branch — never inside a helper that a branch might call twice. This is the sort of constraint that is invisible until it deadlocks.

Install, per kind

The user never declares a kind. The installer picks by probing, in this order:

  1. Parse the target. The positional spec is either . or exactly owner/repo (two non-empty segments — full URLs are rejected); a local path uses --from-path. The repo must already begin with flox- (extract_extension_name strips that prefix to derive the name) — there is no auto-prefixing, so acme/hello is an error; you must pass acme/flox-hello.
  2. Reject conflicts. A name colliding with a built-in top-level subcommand is refused outright against the list in reserved.rs. An already-installed name is refused unless --force.
  3. Probe for a release asset. If the latest release (or the pinned tag) has an asset matching the host platform, this is a binary-kind install: download, verify sha256, extract if archived, chmod +x.
  4. Otherwise clone. Script kind: git clone the repo, verify an executable flox-<name> exists at the root.
  5. Or read a local directory. --from-path skips GitHub entirely and copies the executable and manifest out of the directory (fs::copy) into the managed install dir.

Binary asset resolution

The resolver github::resolve_asset can try up to four strategies, but both production call sites — install and upgrade — invoke it with no manifest, so in practice only two run:

#StrategyRuns in production?Detail
1Explicit platform mapneverA reserved code-comment slot for a future BinaryMeta.platforms; unimplemented.
2Manifest template, exact matchneverImplemented — renders [extension.binary].asset — but install/upgrade pass None as the manifest, so it is dead code in the install path.
3Substring matchyesThe actual selector. Platform tokens matched against asset names — Apple Silicon tries darwin-aarch64, darwin-arm64, macos-aarch64, macos-arm64.
4Rosetta fallbackyesOn Apple Silicon with no arm64 match, retry the x86_64 tokens and log a tracing::info!.

The consequence: the author-facing asset template does nothing, and the much-discussed {os}=macos-not-darwin rendering is moot — no template is rendered during a real install. Selection is substring-only, and the matchers accept both darwin and macos. This reads as a wiring bug (install should pass the manifest); flagged for the code review. Detail on the manifest page.

Upgrade, per kind

  • Binary — resolve the latest release; if the tag is unchanged report up-to-date, otherwise re-run the install flow into a staging directory and rename atomically.
  • Script and git — fetch the tracked ref and reset hard to it, recording the new commit SHA in state.toml. state.toml carries a branch field for exactly this: the default branch observed at install time, so upgrade knows what to fetch.
  • Local — refuses. A local install is a one-time copy from the source directory, with no remote to re-fetch; there is nothing to upgrade, and saying so is better than pretending.
  • Pinned anything — skipped with a notice unless --force.

--dry-run runs resolution only and prints what would happen. Aligning dry-run output with real upgrade output took a dedicated fix (5b9f1817a) for the case where a binary extension has no release at all — a reminder that a dry run is only useful if it is honest about the failure cases too.

One environment variable exists as a test seam, not a feature. FLOX_EXTENSIONS_GITHUB_BASE_URL points the API client at a mock server for the integration tests; it is documented in-code as test-only. It does not redirect git clone, whose host is hardcoded to https://github.com. There is no FLOX_EXTENSIONS_GITHUB_CLONE_HOST and no GitHub Enterprise support.

Testing

Unit

Inline #[cfg(test)] per module. Manifest round-trips, path composition, the resolve_mode truth table, and asset resolution against canned release JSON.

Mocked HTTP

httpmock plus the base-URL override, wrapped in temp_env::async_with_vars so the override is scoped to the test rather than leaking across the suite.

Integration

27 tests covering install from every source, pinning, upgrade, all three activation modes, a gh-parity smoke block translated from gh's own tests, and a drift guard that walks every visible top-level command and asserts the installer refuses it.

The fake-GitHub fixture

The bats suite needs a GitHub that is not GitHub. The technique, from extension.bats::_setup_github_fixture: run a Python http.server on a random port for the API, and redirect clone traffic to a local bare repository using git's insteadOf rewriting — injected per-process through GIT_CONFIG_COUNT and GIT_CONFIG_KEY_<n> environment variables rather than git config --global, because the bats suite shares one global config and parallel files would contend on it.

That constraint has teeth elsewhere too: only coreutils and gnutar are on PATH inside bats, so archive fixtures are built with python3 -c 'import tarfile; …' rather than by shelling out to gzip or curl, which are simply absent.
