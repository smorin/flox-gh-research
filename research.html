The design document, read closely

A PRD and technical plan for porting gh extension to flox extension, written before any code existed. It is unusually explicit about what it does not know — which turns out to be the most useful thing about it.

What the document is

Four parts: a product requirements document, a technical architecture with Rust trait sketches, a component-by-component mapping from Go to Rust, and a six-milestone implementation plan. It names its two reference points precisely — github.com/cli/cli as the implementation being ported and github.com/flox/flox as the target — and scopes itself to a v1 minimum viable port with a roadmap sketched through v3.

It marks its own uncertainty

The most unusual feature of the document is a sourcing note in the header and a whole appendix devoted to what the author could not verify. Claims derived from third-party mirrors, PR discussions, and community blog posts rather than a direct read of main are tagged [verify] inline. Appendix A then lists exactly which files an implementing engineer should open first to confirm the shapes the design depends on.

Appendix A closes with a line that does more work than its length suggests: any discrepancy with this document should be resolved in favor of what's in the repos; the design decisions here do not depend on any particular line number, only on the presence of the named concepts.

That sentence is what lets the implementation diverge from the document without the document becoming wrong. It pre-authorizes the drift — which is worth remembering when you reach the manifest page and find that the shipped schema is not the designed one.

Part one — the product argument

The problem

Flox users had no first-class way to extend the CLI. Every "extend flox" use case — org-specific wrappers, domain workflows, integrations that should not live in the core repo — had to be distributed as shell aliases, standalone binaries on PATH, or custom Nix expressions. The document's indictment of those three is precise: none compose with the flox environment model, none have a discovery or update story, and none make it obvious to a user that they are invoking an extension rather than a core command.

Why now — three forces

Force one

Activation was rewritten

The activation subsystem became Rust in v1.9 and now exec()s the child in place. An extension can therefore be a subprocess of an activation with exactly the same PID semantics as any other activated command.

Force two

FloxHub is not ready to be the only channel

FloxHub is the obvious long-term distribution surface, but GitHub is where the community already is. Building GitHub-first buys adoption without foreclosing FloxHub.

Force three

The gh design is small and proven

Roughly 2,000 lines of production Go in pkg/cmd/extension/, mapping cleanly onto primitives flox already uses — reqwest, toml, shell-out git, and bpaf subcommands.

Goals, and the six non-goals stated to be argued with

The goals are unsurprising: install, list, remove, and upgrade from GitHub; support the three gh flavors; dispatch unknown flox <name> invocations; inherit the active environment by default; let a manifest declare a required environment; and abstract the source so FloxHub can be added later without breaking changes.

The non-goals are the more interesting list, because the document says outright that they are stated so reviewers can see them rather than discover them:

Non-goalStated rationale
No sandboxingAn extension runs with the user's full privileges, exactly like gh. Trust is by code review, not technical enforcement.
No signature verificationA checksum is recorded but not verified. gh's build-provenance attestation is called interesting but out of scope.
No curated registryDiscovery in v1 is searching the flox-extension GitHub topic. A registry follows FloxHub.
No search, browse, create, or execDeferred to v2 and v3.
No binary re-publish layerRelease assets are pulled straight from GitHub.
No overriding of built-in commandsConflicts are rejected at install time.

Two of these did not survive contact with implementation, and both moved in the safer direction. search shipped anyway, as P08. And the checksum non-goal partly reversed — commit f692e3016 added verification of the author manifest's own sha256 against the download (not a GitHub-advertised digest, which does not exist). See the risks page for the full sequence.

Part two — the five primitives kept and the one thing changed

The document is explicit that this is a port, not an inspiration. It names five architectural primitives preserved from gh one-to-one, and exactly one place where flox deliberately diverges. That framing is the spine of the whole design.

Kept from gh, unchanged

  1. The manager as sole orchestrator. Same methods, same name — an ExtensionManager owns install, list, remove, upgrade, and lookup. Nothing else mutates the extensions directory.
  2. A per-extension directory holding the executable plus managed metadata. Same storage shape as gh; only the metadata file's name and format change (state.toml rather than manifest.yml).
  3. Three kinds detected in the same order. Try a release with matching assets first, fall back to cloning. The user never declares which kind they are installing.
  4. Dispatch by searching the managed directory, then $PATH. Managed first, because that directory is populated only by an explicit install — its precedence reflects user intent rather than ambient shell state.
  5. Asset-name substring matching with an explicit override. The installBin algorithm reproduced literally, including the Apple Silicon to x86_64 Rosetta fallback, plus an author-supplied template on top.

Two of these five are what the document proposed, not what the code did. There is no ExtensionManager trait or struct — install, list, remove, and upgrade are free functions in manager.rs, and lookup is dispatch::find; the "same name" was not kept. And the author-supplied asset template is implemented in the resolver but never invoked by install/upgrade (they pass no manifest), so selection is substring-matching only — the "override on top" does not run. The other three primitives hold.

The one deliberate divergence

An extension may declare the flox environment it runs inside. A gh extension cannot express anything like this, because gh has no concept of an environment. This is the single place the design departs from its reference implementation, and the document is careful to say so — it is the only place flox deliberately diverges.

Concretely: the author manifest gains an [environment] stanza, and dispatch gains a three-way mode. The extension either inherits whatever the user has activated (the default), explicitly runs outside any environment, or pins a named environment that is activated for every invocation regardless of what the caller had.

The design defends the default choice for the pinned case directly. When an author pins an environment and the user is also inside one, the pinned environment wins:

An author who pins an environment does so because their extension needs it. Silently falling through to the user's env would be a footgun.

A strict alternative that errors instead is offered, and a third option that composes the two environments is deferred explicitly on the grounds that flox composition semantics were still evolving. All three of those decisions shipped. The mechanics are on the manifest page; the runtime behavior is on the architecture page.

Part three — the Go to Rust mapping

An eighteen-row table pairing each gh component with its proposed flox equivalent, naming both the Go file in cli/cli and the Rust file to create. A representative slice:

gh componentProposed flox equivalent

$XDG_DATA_HOME/gh/extensions/$XDG_DATA_HOME/flox/extensions/
manifest.ymlstate.toml

gh-extension-precompile Actionflox-extension-precompile v2, not built

The mapping largely held up: most proposed filenames exist today with roughly the proposed contents, and the module tree on the architecture page is recognizably this table made real.

With one row that did not survive. The ExtensionSource trait — the abstraction meant to let FloxHub become a second source without breaking changes — was never written. source.rs exists as a single-line comment reading stub for P03, and the proposed floxhub.rs was never created at all.

That is notable because abstracting the source was listed as a v1 goal, not a v2 item. GitHub logic ended up living directly in github.rs and manager.rs with no trait boundary. See the change inventory for what that costs P09.

Part four — the plan, and how it actually went

Seven milestones sized in engineer-weeks, ordered by dependency, each independently shippable behind a FLOX_EXTENSIONS_ENABLE feature flag. Total estimate: roughly ten engineer-weeks for one engineer, or about four calendar weeks for two, with only the environment milestone requiring deep familiarity with flox-activations.

MilestoneSizeBecameOutcome
M0 Skeleton and dispatchSP01as designed
M1 Manifest, layout, local installMP02as designed
M2 GitHub source — git/scriptMP03as designed
M3 GitHub source — binary releaseMP04as designed
M4 Upgrade-all and polishSP05as designed
M5 Environment integrationMP06as designed
M6 Docs, telemetry, GASP07telemetry deferred
——P08search, pulled forward from v2

The plan is the rare case of an estimate that held its shape. The dependency order was followed, every milestone landed, and the two deviations both went the direction you would want: one deferred item was the least load-bearing thing on the list, and one v2 feature arrived early.

What changed relative to the plan

  • Telemetry was cut, not slipped. P07-T04 and P07-TS03 are marked [~] — deferred per design review; revisit post-GA — rather than left open. The GA criterion was met without them.
  • The feature flag inverted rather than disappeared. The plan said remove FLOX_EXTENSIONS_ENABLE at GA. What shipped is FLOX_FEATURES_EXTENSIONS defaulting to on, with the env var retained as an opt-out. The later rebase (P11) reversed this again, dropping the bespoke flag for the pre-existing features.beta, off by default. Setting it to 0, false, no, or off disables both the subcommand family and the dispatch fallback.
  • Example repos moved out of the GA milestone. M6 listed them as a deliverable; they became separate projects P07a, P07b, and P07c so GA did not block on them.
  • The example org changed twice. The plan put the reference extensions in flox-examples; they were first published under smorin, then transferred to the flox org, where they live now. Doc references were reconciled at each step — see the risks page.

What the document asked to be checked later

Section 2.11 lists seven open questions rather than pretending they were resolved. Their current status, which is the useful part:
