Deliberate wiring · 7 pre-existing files

This is the section that matters. Everything above could be deleted without flox noticing; these seven edits are what make the new code reachable, and they are therefore the only places a regression can originate. Each is shown verbatim.

cli/flox/src/main.rs

+3 / −0 · the highest-leverage change in the branch

The binary's entry point. Its main runs the bpaf parser and matches on the result; the ParseFailure::Stderr arm is what prints "unknown command" errors and exits non-zero.

What changed

Three lines inserted at the top of that arm: before printing the error, ask whether the failed parse might have been an extension invocation.

cli/flox/src/main.rs@@ -137,6 +137,9 @@
             bpaf::ParseFailure::Stderr(m) => {
+                if let Some(exit) = commands::extension::try_dispatch_external() {
+                    return exit;
+                }
                 message::error(format!("{m:80}"));
                 return ExitCode::from(1);
             },

Impact and architecture

Placement is the entire design. Because the hook sits inside the failure arm rather than before the parser, the successful path is untouched — no extension code executes on any invocation that parses. And because it precedes message::error, a matched extension runs instead of the error, while an unmatched one falls through to the identical error flox would have printed anyway. try_dispatch_external returning Option is what makes that fall-through possible.

It is also where the residual risk concentrates: these three lines run on every failed parse of every flox command, for every user, installed extensions or not. That is the blast radius in its entirety, and it is three lines wide.

Impact and architecture

The variant is added at the bottom of the enum, and this is a stated constraint rather than a coincidence. PROJECTS.md requires new variants on the top-level enum in preference to expanding an existing group enum, on the reasoning that appending to Commands touches only the end of a list plus one match arm, whereas adding under a group like ManageCommands would mutate a structure belonging to unrelated commands. The additive change was chosen because it is the one that cannot disturb anything else.

During the prototype window the variant also carried #[bpaf(hide)], so builds without the feature flag produced byte-identical help output to stock flox. The GA commit removed it.

The other eighty lines

An extension_drift_tests module that scrapes flox --help and asserts every visible top-level command appears in RESERVED_COMMAND_NAMES. It exists because bpaf exposes no programmatic command enumeration, making help-text parsing the only mechanism available — a workaround the module documents rather than hides.

Its doc comment also states the shadowing rule outright: a top-level subcommand always shadows an extension of the same name. The test keeps the reserved list in sync so install-time rejection stays correct; it cannot help with an extension installed before flox gains a conflicting command. Discussed on the risks page.

Impact and architecture

That single deleted line is the most consequential removal in the branch. Default had to stop being derived because a derived Default gives every bool the value false, and this flag needs to default to true. The explicit impl is the cost of a default-on feature.

It changes behavior for the other two flags only in that they are now stated rather than inferred — upload and qa remain false. The added PartialEq/Eq exists to support the accompanying test, which asserts on the whole struct rather than one field. That follows the repo's own convention: use assert_eq! on entire structs so failures are easier to debug and new fields are caught. A future flag added without updating this test will fail it, which is the intent.

The #[serde(default = "default_true")] attribute matters separately: it means an existing config file written before this field existed deserializes with extensions enabled, rather than silently off.

Impact and architecture

Two lines that explain a technique described on the architecture page. The bats suite stands up a fake GitHub using a Python http.server on a random port, and builds archive fixtures with python3 -c 'import tarfile; …' — because gzip, unzip, and curl are simply absent from that PATH. Adding a test that shells out to something new means editing this file too, and the failure mode is a confusing "command not found" inside a sandbox.

What the shape of this diff proves, and what it does not

What it proves

The isolation claim is real and measurable. Seven files of wiring, 127 added lines, three removed. Reverting the branch is mechanically simple: delete two directories and four files, revert seven small edits. Nothing was refactored on the way past, and no existing abstraction was bent to accommodate the new code.

What it does not prove

A small diff is not a safe diff. The three lines in main.rs execute on every failed parse for every user; the Features change alters a default that ships on. Line count measures reviewability, not risk. Both of those edits deserve more scrutiny per line than the 2,432-line manager.rs, which cannot run unless someone invokes it.

One thing to know before reading the branch

The working tree is not clean. Three tracked files carry uncommitted changes — cli/tests/extension.bats (+118 lines over its committed state), .gitignore, and the generated catalog client — alongside untracked .factory/, docs/superpowers/, and a .DS_Store.

All figures on this page are the committed state. CLAUDE.local.md anticipates exactly this and gives the rule that follows from it: never git add . or git add -A on this branch — stage specific paths, or unrelated long-lived work gets swept into a feature commit.
