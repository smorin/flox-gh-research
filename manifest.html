The author's contract

One optional TOML file at the repo root is the entire surface an extension author declares. This is every field it can hold, why each exists, and the three places the shipped schema parted ways with the one that was designed.

Why the file exists at all

An extension can work without it. The name is derivable from the repository (flox-hello becomes the hello extension), the kind is inferred by probing for release assets, and the default activation behavior needs no declaration. Two of the three reference extensions ship manifests of four lines.

The manifest earns its place in exactly two situations:

Binary extensions need it

Release assets have names, and flox has to guess one. The manifest lets an author state the naming scheme rather than hope the substring matcher finds the right file. This is the only case the author guide calls required.

Environment behavior needs it

The [environment] stanza is the one thing that cannot be inferred from repo shape. An extension that must run inside a particular flox environment has no way to say so except here.

The minimal manifest

flox-extension.tomlthe whole thing
schema = "1"

[extension]
name = "hello"

And in practice, even schema gets omitted — it has a serde default of "1", and two of the three reference extensions leave it out. Whether that is pragmatism or a schema-versioning discipline already eroding is discussed below.

The full manifest

flox-extension.tomlevery field the parser accepts
schema = "1"

[extension]
name        = "deploy"
description = "Deploys things"

[extension.binary]
source = "github-release"
asset  = "flox-deploy-{os}-{arch}.tar.gz"
sha256 = "cafe..."

[environment]
mode         = "pinned"
inherit_name = "flox-examples/dev"

[on_active]
inside = "error"

[extension]

FieldTypeWhat it does and why
namestringrequired The extension name, without the flox- prefix. Must match the repo's <name> segment. Lowercase, matching [a-z0-9][a-z0-9_-]*. This is what the user types after flox, and what the installer checks against the reserved-name list.
descriptionstringoptional Short human description, surfaced in list and search output. Purely presentational — nothing branches on it.

[extension.binary]

Present only for binary-kind extensions. Its absence is not a declaration that the extension is not binary — kind is still inferred by probing for release assets — but without it the installer has only substring matching to work with.

FieldTypeWhat it does and why
sourcestringrequired Only "github-release" is accepted today. It exists as a field rather than an assumption so that a future FloxHub or direct-URL source can be added without a schema bump — the same forward-compatibility move as state.toml's source discriminant.
assetstringrequired Asset-name template. Placeholders {name}, {os}, {arch}, and {ext} are expanded, then matched against release asset names exactly. Read the placeholder note below before writing one.
sha256stringoptional Documented as "reserved for future verification." Note that this is not the digest that gets verified at install time — see the verification note below, which is a genuine subtlety.

The placeholder that does not do what the docs say

The author guide states {os} renders as "darwin", "linux", or "windows". It does not. render_asset_template substitutes Rust's raw std::env::consts::OS, which is "macos" on macOS. Only {ext} is computed — "zip" on Windows, "tar.gz" everywhere else.

The flox-hello-binary reference repo is correct and the documentation is wrong: its assets are named flox-hello-binary-macos-aarch64.tar.gz, which is exactly what the template renders.

What makes this hard to notice is that following the incorrect documentation still works. An author who ships ...-darwin-aarch64.tar.gz fails the exact template match, falls through to substring matching — which accepts darwin and macos — and installs successfully. A wrong doc, masked by a forgiving fallback, is the kind that survives for years.

What sha256 actually verifies

Commit f692e3016 added digest verification, and the distinction matters. The digest checked at install time is the one GitHub advertises for the release asset, compared against what was actually downloaded — it detects a corrupted or truncated transfer. The sha256 field in your manifest is not that check. Do not treat a manifest digest as a supply-chain guarantee; see the risks page for what the trust model does and does not cover.

[environment]

The stanza with no gh equivalent. Omit it entirely and you get inherit, which is right for most extensions.

FieldTypeWhat it does and why
modestringrequired One of "inherit", "none", "pinned". Anything else logs a warning and degrades to inherit rather than failing dispatch, so a manifest written against a future schema does not break on an older flox.
inherit_namestringrequired when pinned An <owner>/<environment> reference valid for flox activate -r. If mode = "pinned" and this is missing or empty, flox warns and falls back to inherit — a malformed manifest degrades rather than hard-failing.
inheritenuminert Accepts "current", "default", "named". Parsed, round-tripped, and never read. The author guide documents it honestly as "reserved for future use; not consumed by flox today."

The three modes, in one table

ModeWhat happens at dispatchReach for it when
inherit
default		 Exec directly. Every FLOX_* variable the caller had is preserved. Almost always. The extension behaves like any other command run at the prompt.
none env_clear(), replay every non-FLOX_ variable, then overlay the four bookkeeping vars. FLOXHUB_* deliberately survives. The extension must not be influenced by caller-side flox state — a diagnostic that reports on flox itself, or an auditor needing a clean baseline.
pinned Already inside that environment? Exec directly. Otherwise wrap with flox activate -r <ref> -- <ext>. The extension genuinely cannot run without specific tooling — a deploy script that needs the team's toolchain, whatever the user happens to have active.

[on_active]

A separate top-level table, not nested under [environment], governing one narrow question: what to do when mode = "pinned" and the caller is already activated in a different environment.

FieldValuesBehavior
inside "override" default Wrap with flox activate -r unconditionally. The author pinned an environment because the extension needs it; falling through to the user's would be a footgun.
"error" Refuse with PinnedEnvMismatch, whose message names the exact flox activate -r <ref> --trust command needed to proceed.

schema

Always the string "1". Deliberately not the type-state Manifest<S> pattern that flox-manifest uses for environment manifests — the module comment gives the reason plainly: there is one schema version and no migration history, so the machinery would be cost without benefit.

state.toml — the other half

Where flox-extension.toml is authored and committed, state.toml is written by the installer into the install directory and read by list, remove, and upgrade. Users are not meant to edit it.

~/.local/share/flox/extensions/flox-hello/state.toml
schema       = "1"
name         = "hello"
kind         = "script"        # script | binary | local
source       = "github"        # github | .           ← the future-FloxHub discriminant
owner        = "smorin"
repo         = "flox-hello-script"
host         = "github.com"    # supports GitHub Enterprise
tag          = ""              # release tag, for binary kind
branch       = "main"          # default branch at install time; upgrade fetches this
commit       = "c8d5f41..."    # resolved SHA, for script/git kinds
pinned       = false           # true when installed with --pin
asset_sha256 = ""              # recorded for binary kind
installed_at = "2026-04-17T12:34:56Z"
path         = "/home/me/.local/share/flox/extensions/flox-hello/flox-hello"

Why the split is the right call

gh conflates these: a single manifest.yml holds owner, name, host, tag, ispinned, and path, all machine-written. The design document splits the roles explicitly and gives three reasons — the rest of the flox ecosystem is TOML, flox already depends on toml and toml_edit, and gh's file is internal state rather than an author-facing surface, so conflating them was never really a design choice in the first place.

The practical payoff is that the author-facing schema can stay tiny and stable while the internal record grows whatever fields the installer needs. branch is the proof: it was added because upgrade needs to know which ref to fetch, and it cost authors nothing.

Designed versus shipped

The design document specified a manifest schema in detail. The shipped one is different in almost every particular. This is not a defect — the document explicitly pre-authorized it — but anyone reading the design document as documentation will write manifests that do not parse.

AspectDesignedShipped
schema type schema = 1 integer schema = "1" string breaks parse
Binary block asset_template plus an explicit [extension.binary.platforms] map source + asset + sha256; the platforms map is a reserved comment slot in resolve_asset_for renamed
Environment block inherit = "inherit"|"none"|"pinned", ref, and on_active all inline in [environment] mode + inherit_name, with on_active promoted to its own top-level table restructured
kind field Author-declarable: "script", "binary", "git" Does not exist. Kind is always inferred by probing. simplified
Metadata fields version, license, homepage None of them. ExtensionMeta holds name, description, binary. cut
Local install flox extension install . flox extension install --from-path . renamed
index.toml An optional name-to-directory cache at the extensions root Not built — lookup is a single path join, so a cache earned nothing dropped

Reading the drift

Three of these are unambiguous improvements. Dropping the author-declarable kind removes a field that could contradict reality — a repo declaring kind = "binary" with no release assets would be a lie the installer had to reconcile. Cutting version, license, and homepage removes three fields that duplicate what GitHub already knows and nothing branched on. Dropping index.toml removes a cache with no measured benefit.

The renames are the ones that cost something. inherit became mode while a different field named inherit was introduced with unrelated semantics and then never read — so the design document and the shipped schema both have a field called inherit, meaning different things, one of them inert. That is the single most confusing artifact of the drift, and it is the reason the author guide has to spend a table row telling readers a documented field does nothing.

For a maintainer, the practical consequence: the design document is a reliable guide to intent and an unreliable guide to syntax. When the two disagree about a field name or type, the code is authoritative — which is exactly what the document's own Appendix A asked for.
